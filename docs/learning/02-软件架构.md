# 软件架构

## 架构概览

Microduck 采用**微服务架构**，7 个独立的守护进程通过 Unix socket 通信，每个进程负责特定职责，故障隔离，可独立重启。

```
┌─────────────────────────────────────────────────────────┐
│                      客户端层                            │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐  ┌────────┐ │
│  │  手柄    │  │  手机App │  │ 笔记本CLI│  │ WebRTC │ │
│  │  (BLE)   │  │  (BLE)   │  │  (SSH)   │  │(浏览器)│ │
│  └────┬─────┘  └────┬─────┘  └────┬─────┘  └───┬────┘ │
└───────┼──────────────┼──────────────┼────────────┼──────┘
        │              │              │            │
        └──────────────┴──────────────┴────────────┘
                       │
              ┌────────▼────────┐
              │   传输适配层     │
              │  ┌────────────┐ │
              │  │   btd      │ │  ← BLE 适配
              │  │   padd     │ │  ← 手柄适配
              │  │   mediad   │ │  ← WebRTC 适配
              │  └─────┬──────┘ │
              └────────┼────────┘
                       │ JSON-RPC 2.0 (NDJSON)
              ┌────────▼────────┐
              │   核心服务层     │
              │  ┌────────────┐ │
              │  │  robotd    │ │  ← 控制循环 (50Hz)
              │  │  configd   │ │  ← 配置管理

              │  │  tofd      │ │  ← ToF 传感器
              │  └─────┬──────┘ │
              └────────┼────────┘
                       │
              ┌────────▼────────┐
              │   硬件抽象层     │
              │  ┌────────────┐ │
```

## 守护进程详解

### 1. robotd — 控制守护进程

**职责**: 50Hz 控制循环，策略推理，安全保护

**关键组件**
```
robotd/
├── src/
│   ├── main.rs          # 入口，IPC 服务器
│   ├── control.rs       # 控制逻辑，策略调度
│   ├── safety.rs        # 安全层，borrow checker 强制
│   └── ipc.rs           # JSON-RPC 处理
```

**核心循环**
```rust
loop {
    // 1. 读取传感器 (2ms)
    let sensors = io.read()?;  // sync_read 16 个设备
    
    // 2. 构建 observation (0.1ms)
    let obs = Observation::build(&sensors, &command);
    
    // 3. 策略推理 (2ms)
    let action = policy.infer(&obs)?;
    
    // 4. 安全过滤 (0.1ms)
    let targets = safety.apply(action, &sensors);
    
    // 5. 写入舵机 (2ms)
    io.write(&targets)?;  // sync_write 15 个舵机
    
    // 6. 等待下一个周期
    sleep(Duration::from_millis(20) - elapsed);
}
```

**设计原则**
- **独占 IO**: 只有 robotd 能访问 `/dev/ttyS2`
- **实时性**: 50Hz 硬实时，错过周期立即丢弃
- **安全优先**: 任何异常立即进入安全模式

### 2. updaterd — 更新守护进程

**职责**: OTA 更新，签名验证，原子替换，健康检查，自动回滚

**关键组件**
```
updater/
├── src/
│   ├── main.rs          # 入口，IPC 服务器
│   ├── engine.rs        # 更新引擎
│   ├── verify.rs        # 签名验证
│   ├── store.rs         # 版本管理
│   └── health.rs        # 健康检查
```

**更新流程**
```
1. 下载新版本 (manifest + artifact)
   ↓
2. 验证签名 (minisign)
   ↓
3. 解压到临时目录
   ↓
4. 原子替换 current symlink
   ↓
5. 重启所有守护进程
   ↓
6. 健康检查 (30s 超时)
   ├─ 成功 → 提交更新
   └─ 失败 → 自动回滚
```

**设计原则**
- **原子性**: symlink 替换是原子操作
- **可回滚**: 保留上一个版本
- **安全验证**: 所有更新必须签名
- **健康门控**: 不健康自动回滚

### 3. configd — 配置守护进程

**职责**: WiFi 管理，身份配置，NetworkManager D-Bus 控制

**关键组件**
```
configd/
├── src/
│   ├── main.rs          # 入口，IPC 服务器
│   ├── wifi.rs          # WiFi 管理
│   ├── identity.rs      # 机器人身份
│   └── nm_client.rs     # NetworkManager D-Bus 客户端
```

**配置存储**
```
/etc/robot/
├── updater.toml         # 更新配置
├── robotd.toml          # 控制配置
└── trusted_keys/        # 信任的公钥
    └── release.pub
```

**设计原则**
- **持久化**: 配置写入 /etc，重启保留
- **D-Bus 集成**: 通过 NetworkManager 管理 WiFi
- **安全隔离**: 配置文件权限 600

### 4. btd — 蓝牙守护进程

**职责**: BLE GATT 服务器，手机 App 接入

**关键组件**
```
btd/
├── src/
│   ├── main.rs          # 入口，BLE 服务器
│   ├── gatt.rs          # GATT 服务定义
│   └── adapter.rs       # BlueZ 适配器
```

**BLE 服务**
```
Microduck Service (UUID)
├── robot.control        # 控制指令 (Write)
├── robot.status         # 状态上报 (Notify)
├── robot.config         # 配置读写 (Read/Write)
└── robot.update         # 更新控制 (Write)
```

**设计原则**
- **传输适配**: 只转发 IPC 调用，不实现业务逻辑
- **低功耗**: BLE 5.0，优化广播间隔
- **安全配对**: BLE 配对 + 加密

### 5. padd — 手柄守护进程

**职责**: 读取手柄输入，转换为控制指令

**关键组件**
```
padd/
├── src/
│   ├── main.rs          # 入口，手柄读取
│   ├── evdev.rs         # Linux evdev 接口
│   └── mapping.rs       # 按键映射
```

**手柄映射**
```
左摇杆: 前进/后退/转向
右摇杆: 头部俯仰/偏航
A 按钮: 踢球
B 按钮: 翻滚
X 按钮: 捡东西
Y 按钮: 坐下/站起
```

**设计原则**
- **低延迟**: 事件驱动，立即转发
- **多手柄**: 支持同时连接多个手柄
- **自动重连**: 手柄断开自动重连

### 6. mediad — 媒体守护进程

**职责**: 摄像头采集，硬件编码，WebRTC 推流

**关键组件**
```
mediad/
├── src/
│   ├── main.rs          # 入口，WebRTC 服务器
│   ├── pipeline.rs      # GStreamer 管线
│   ├── webrtc.rs        # WebRTC 信令
│   └── console.rs       # Web 控制台
```

**GStreamer 管线**
```
v4l2src → videoconvert → mpph264enc → webrtcbin
         (RGB)          (硬件编码)    (WebRTC)
```

**设计原则**
- **硬件编码**: 使用 Rockchip MPP，减轻 CPU 负担
- **低延迟**: WebRTC，端到端 <200ms
- **独立进程**: 媒体崩溃不影响机器人控制

### 7. tofd — ToF 守护进程

**职责**: ToF 传感器读取，深度数据发布

**关键组件**
```
tof/
├── src/
│   ├── main.rs          # 入口，IPC 服务器
│   ├── sensor.rs        # VL53L5/8CX 驱动
│   └── publisher.rs     # 数据发布
```

**数据格式**
```rust
struct DepthFrame {
    width: u32,          // 8
    height: u32,         // 8
    data: Vec<u16>,      // 64 个像素，单位 mm
    timestamp: u64,
}
```

**设计原则**
- **发布-订阅**: 其他服务可以订阅深度数据
- **独立进程**: ToF 初始化慢（~2s），不阻塞控制循环
- **可选组件**: 没有 ToF 传感器也能运行

## IPC 设计

### 协议：JSON-RPC 2.0

**格式**: NDJSON (Newline Delimited JSON)
```json
{"jsonrpc":"2.0","id":1,"method":"robot.move","params":{"vx":0.5,"vy":0.0,"vyaw":0.1}}
{"jsonrpc":"2.0","id":1,"result":null}
```

**为什么选 JSON-RPC？**
- **人类可读**: 调试方便
- **标准协议**: 广泛支持
- **灵活**: 支持通知（无 id）
- **轻量**: 比 gRPC 简单

### 传输：Unix Socket

**路径**: `/run/robotd.sock`
**权限**: 660 (root:robot)
**认证**: SO_PEERCRED (uid/gid/pid)

**为什么选 Unix Socket？**
- **安全**: 文件系统权限控制
- **高效**: 无网络栈开销
- **简单**: 不需要端口管理

### 认证：SO_PEERCRED

```rust
let cred = socket.peer_cred()?;
let uid = cred.uid();
let gid = cred.gid();

// 检查是否允许调用
if !allow_uids.contains(&uid) && !allow_gids.contains(&gid) {
    return Err(PermissionDenied);
}
```

**设计原则**
- **零信任**: 每个调用都验证身份
- **最小权限**: 只允许必要的 uid/gid
- **审计**: 记录所有调用来源

## 状态管理

### 配置状态

**位置**: `/etc/robot/`
**特点**: 持久化，手动编辑

### 运行时状态

**位置**: `/run/<daemon>/`
**特点**: 临时，重启清除

```
/run/robotd/
├── identity.json        # 运行时身份
└── state.json           # 运行时状态
```

### 更新状态

**位置**: `/var/lib/robot/updater/`
**特点**: 持久化，fsync 保证

```
/var/lib/robot/updater/
├── current -> releases/0.10.0/
├── releases/
│   ├── 0.9.0/
│   └── 0.10.0/
└── update-log.jsonl     # 更新日志
```

## 故障隔离

### 进程隔离

每个守护进程独立运行，一个崩溃不影响其他：
- **robotd 崩溃**: 舵机保持最后位置，其他服务继续运行
- **mediad 崩溃**: 视频流中断，机器人继续行走
- **updaterd 崩溃**: 无法更新，机器人正常运行

### 重启策略

```ini
# systemd 配置
[Service]
Restart=always
RestartSec=5
WatchdogSec=30
```

**设计原则**
- **自动重启**: 崩溃后 5s 自动重启
- **看门狗**: 30s 无响应自动重启
- **依赖管理**: 关键服务重启会触发依赖服务重启

## 性能优化

### 1. 零拷贝

**问题**: 摄像头帧数据大（~1MB/帧）
**解决**: 使用 dmabuf 共享内存

```rust
// mediad 分配 dmabuf
let buf = dmabuf_alloc(1920 * 1080 * 3);

// 传递给 robotd（只传 fd）
let fd = buf.as_fd();
ipc.send(RpcMessage::Frame { fd });
```

### 2. 异步 IO

**问题**: 网络 IO 阻塞主循环
**解决**: Tokio 异步运行时

```rust
tokio::spawn(async {
    let frame = camera.read().await;
    encoder.encode(frame).await;
    webrtc.send(frame).await;
});
```

### 3. 缓存

**问题**: 频繁读取配置
**解决**: 内存缓存 + inotify 监听

```rust
struct ConfigCache {
    config: Arc<RwLock<Config>>,
    watcher: inotify::Inotify,
}

// 配置变更时自动更新
watcher.watch("/etc/robot/robotd.toml", WatchMask::MODIFY);
```

## 总结

Microduck 的软件架构体现了以下原则：

1. **微服务**: 职责单一，故障隔离
2. **松耦合**: 通过 IPC 通信，可独立部署
3. **安全优先**: 权限控制，签名验证
4. **实时性**: 50Hz 硬实时，错过即丢弃
5. **可观测**: 日志、指标、状态暴露

这种架构使得 Microduck 能够在有限的硬件条件下实现复杂的功能，同时保持良好的可维护性和可扩展性。
